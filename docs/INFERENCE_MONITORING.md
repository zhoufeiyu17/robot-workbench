# 推理链路独立监控

2026-11-14，用户确认实施。职责与用例同步到架构目录中的 Monitoring 模块、UC22 与 I18。

## 职责

生产组件提供有界数字探针，独立监控进程读取诊断接口、关联故障和保存证据。监控进程按自身生命周期启停，只持有读取与写入自身诊断目录的能力。接入、释放、动作执行、模型调用和恢复由原组件负责。

既有 `pipeline_timing.py` 保留细分耗时统计。`runtime_monitor.py` 管理近期数字状态、分析与故障记录；`scripts/monitor_inference.py` 提供独立运行入口。`monitored_memory.py` 在组合层观察既有 MemorySession，模型适配器及其制品指纹保持独立。原临时 MEM 监控的有效检查归入该模块，GPU 归属与小时租约核验仍遵循资源管理入口。

## 用例与完成条件

| 用例 | 触发与证据 | 完成条件 |
| --- | --- | --- |
| 正常运行 | 图像、元数据、状态、配对、MEM阶段持续推进 | 有界内存维护最近状态，正常轮询不写全量时间线 |
| 输入供应异常 | G03首次拒绝、G07/G08超时 | 保存异常前约5秒和后约1秒数字时间线，关联两端Run、epoch、样本和请求 |
| 回调或元数据阻塞 | 活动回调起点、原图与元数据到达、合并完成 | 指出可证实的最早落后阶段；证据不足时保留未知字段 |
| MEM更新核验 | 节点入队、准备、等待模型访问权、写入和完成 | 对照实际节点步距、阶段与模型时间；保留显式节点差异 |
| 监控故障 | 端点不可达、满盘、队列或容量达到上限 | 诊断报告降级和缺口，业务控制继续独立运行 |
| 隔离复现 | 延迟元数据、状态、回调和MEM，制造丢失及重复事件 | 记录准确归因于注入阶段，完成后可用同一数字轨迹重放分析 |

## 数字探针契约

I18采用 `workbench.runtime-monitor.v1`，包含进程/boot身份、单调采样时间、探针序列、各通道最新值、故障游标、丢弃计数及可选近期历史。字段仅允许有界标量，使用现有run_id、epoch、observation_id、request_id和来源序号关联。

| 通道 | 生产者字段 | 消费用途 |
| --- | --- | --- |
| callback | consumer、topic、active、begin/end、RMW接收时间、source_sequence | 区分等待回调和回调内部耗时，识别尚未结束的回调 |
| raw / metadata / ready | consumer、stream、source_ns、sequence、received_ns | 比较原图、元数据和最终可用样本的推进 |
| selection | 最新各路时间、选中各路时间、目标时间、配对状态 | 区分输入落后与配对选择落后 |
| memory | 节点类型/步数/模型时间、request_id、阶段、pending | 核验节点更新，关联输入停顿与MEM活动 |
| fault | 原始规则/原因、run_id、epoch、故障单调时间 | 合并重复异常，跨进程查询与留档 |

RMW接收时间保留时钟属性，代表中间件向应用提供的接收时间。原始源时间、主机wall和monotonic分别保存；跨boot的单调时间不相减。接口未提供的内核/DDS队列长度留空，序号与年龄只描述已观测到的积压。

## 执行与开销

热路径采用非阻塞写入、固定通道数量及每通道有界历史。常规历史最多20Hz；异常和MEM节点边沿单独保留。忙时丢弃诊断更新并累计计数。控制循环中的故障触发只追加小型标记，序列化和文件IO由独立监控进程完成。

监控复用现有HTTP诊断接口，正常约2Hz读取简要状态，故障后读取近期历史。历史按时间和容量双重裁剪；故障文件限制数量与总字节，重复故障合并。原始图像、权重和完整机器人状态引用既有录制；诊断目录只存数字证据。

候选验收预算为新增热路径P99小于10微秒、正常CPU增量低于单核1%。实测报告同时记录控制周期、观测年龄、丢弃计数和故障留档耗时。预算达标需要同负载对照，不能仅凭后台进程或隔离单元测试判定。

4. 将实测开销、故障文件和未覆盖范围写入发布回执，再更新架构状态。

## 运行与诊断

物理工作台启动脚本自动创建独立监控子进程。输出位于该次后端运行目录的 `diagnostics/`，`status.json` 包含读取/写入失败、丢弃计数、缺失的监控来源与最新检查时间。正常状态至少每30秒更新一次。当前实现最多保留16份、每份4 MiB的事故文件，文件名采用固定槽位循环使用。

独立入口接受部署提供的地址及目录。

```sh
python scripts/monitor_inference.py --endpoint '<工作台地址>' --output '<诊断目录>'
python scripts/monitor_inference.py --replay '<诊断目录>/incident-00.json'
```

`GET /api/inference-diagnostics?environment=physical&limit=0&monitor_only=1` 提供轻量探针视图；增加 `monitor_history=1` 读取有界历史。轻量视图跳过细分统计排序和录制文件读取。故障记录包含前后两个进程快照，`complete_post_window` 标识后窗口是否收齐；丢弃计数和进程身份用于判断证据覆盖。

2026-11-14候选验收包含真实相机/状态和当前所选T03模型24次预测，其中12次覆盖测试订阅器中的状态回调阻塞与MEM等待注入。完整制品、短时开销对照及发布事实以 `.evidence/inference-monitor-20261114-v1/` 的回执为准。

## 真机复现后的共享图像缓存修正

2026-11-14随后真机运行再次出现观测过期。该次数字证据显示，独立状态接收年龄最高约15.4ms，推理图像接收落后约100–145ms，同进程相机预览中的原始图像年龄约3–40ms；图像时间元数据回调等待最高约1067ms。该次MEM节点在故障前成功提交。证据定位到推理的独立图像接收路径，具体调度阻塞触发条件尚未稳定复现。

原实现中，预览使用深度1的图像订阅，推理另建深度4的订阅并重复解码。修正让推理借用公共相机视图已校验的原始RGB缓存，保留源身份、发布者身份与源变更失效语义；缓存保留64帧，状态和控制事件仍使用各自独立的执行器。相机输入对象替换后，推理绑定失效并需重新准备。

新验收在SDK动作出口隔离条件下，使用真实三相机、实时反馈、真实模型与标准录制，同时回放故障现场的控制事件，并运行同进程10Hz预览和5Hz状态查询。45.6秒短验收完成50次预测，观测年龄P99为68.6ms、最高74.7ms，录制完整且MEM无错误。610.9秒隔离长验收完成616次预测，观测年龄P99为70.6ms、最大95.8ms，超过100ms次数为0；三路图像及状态流均超过612秒，封存结果为complete，MEM无错误。

旧、新接收器的短时事件回放对照均未自然复现原故障，不能据其延迟差异声称性能提升。后续真实动作验收仍需独立记录。故障及候选证据入口为 `.evidence/arx6-physical-timeout-20261114-v2/` 与 `.evidence/arx6-shared-image-cache-20261114-v1/`。
